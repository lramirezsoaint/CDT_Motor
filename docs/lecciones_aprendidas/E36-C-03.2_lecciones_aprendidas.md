# E36-C-03.2 - Lecciones Aprendidas

## Objetivo

Documentar los hallazgos al implementar `E36-C-03.2`, enfocado en validaciones negativas por campo dentro de `Comunes > Grupo Producto`.

## Problemas encontrados

### 1. El caso exige obligatoriedad por campo, no un único error genérico

La lectura correcta del catálogo no era validar solo un mensaje general, sino:

- intentar vaciar los campos objetivo del modal
- verificar error visible y específico por campo
- bloquear el guardado
- confirmar que la tabla no cambie

### 2. No todos los campos visibles son realmente vaciables

En este modal hay campos que pueden estar:

- visibles
- habilitados
- pero no necesariamente permitir quedar vacíos

También puede haber campos derivados o autocompletados que no deben forzarse como si fueran inputs libres.

### 3. `Nombre Línea` es un campo dependiente

El catálogo lo trata como obligatorio, pero funcionalmente depende de `Código Línea`.

Por eso, si la UI no permite vaciarlo manualmente:

- no debe forzarse la interacción
- sí debe dejarse trazabilidad de que fue omitido por comportamiento real de la UI

## Decisiones tomadas

### 1. Reutilizar el patrón negativo estabilizado de E36-C-03.1

Se reutilizó la misma estrategia base:

- fila editable
- apertura flexible del modal
- validación visual por campo
- bloqueo del guardado
- no mutación de la tabla

### 2. Validar obligatoriedad solo sobre campos realmente vaciables

El test intenta vaciar cada campo objetivo:

- `Código`
- `Nombre`
- `Código Línea`
- `Nombre Línea`
- `Método de Valoración`

Si la UI no permite vaciar alguno:

- no se marca como bug falso
- se deja anotación en la prueba

### 3. Mantener validaciones de formato en los campos textuales editables

Las validaciones de formato se mantuvieron sobre:

- `Código`
- `Nombre`

usando caracteres especiales no permitidos, porque son los campos textuales donde esa regla de negocio sí aplica directamente.

## Diferencias UI vs catálogo

### 1. El catálogo asume campos obligatorios homogéneos

La UI real no necesariamente expone todos esos campos con la misma mecánica:

- algunos son texto libre
- otros son combos
- otros son dependientes/autocompletados

### 2. La cobertura correcta depende del comportamiento real del control

Para mantener fidelidad al caso:

- se valida requerido si el campo puede vaciarse
- se valida formato si el campo acepta edición textual
- no se fuerzan rutas imposibles sobre controles bloqueados o derivados

## Patrones reutilizables

### 1. En modales de edición con combos, distinguir `visible`, `editable` y `vaciable`

No basta con encontrar el campo:

- hay que confirmar si acepta interacción
- y además si realmente puede quedar vacío

### 2. Los errores deben verificarse cerca del campo

La validación robusta por campo debe comprobar:

- marca visual de inválido
- mensaje visible cercano
- permanencia del modal
- bloqueo del `Actualizar`

### 3. La fila base no debe cambiar tras intentos inválidos

Toda validación negativa debe comprobar que:

- el modal sigue abierto o el guardado queda bloqueado
- la fila original no muta en tabla

## Recomendaciones

- Mantener `E36-C-03.2` como caso negativo por campo, no como validación global única.
- Seguir dejando trazabilidad cuando un campo no pueda vaciarse desde la UI real.
- Reutilizar este patrón en `E36-C-03.3`, `E36-C-03.4` y `E36-C-03.5` ajustando solo los campos objetivo del modal correspondiente.
