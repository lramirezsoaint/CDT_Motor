# E36-C-03.1 - Lecciones Aprendidas

## Objetivo

Documentar los hallazgos al implementar `E36-C-03.1`, enfocado en validaciones negativas por campo dentro de `Comunes > Líneas`.

## Problemas encontrados

### 1. Los matchers rígidos fallan con tildes visibles del modal

En una corrida real el flujo sí encontró filas editables y abrió el modal, pero un matcher como:

- `/linea/i`

no coincidió con el texto visible:

- `Editar Línea`

Eso generó un fallo técnico, no funcional.

### 2. El campo `Código` no quedó editable en la UI real

Durante la validación del modal, el locator asociado a `codigo` resolvió un control derivado tipo:

- `codigoLinea`

y ese control apareció deshabilitado. Eso impide forzar una validación negativa sobre ese campo como si fuera editable.

### 3. Obligatorio no siempre significa vaciable

En este módulo hay campos que pueden estar:

- visibles
- habilitados
- pero no permitir quedar vacíos desde la propia UI

Por eso, para validar obligatoriedad fielmente, no basta con detectar el campo: también hay que comprobar si realmente puede vaciarse.

### 4. Los errores relevantes viven en el formulario, no en la tabla

La tabla solo sirve para encontrar la fila base. El valor real del caso está en verificar:

- estado inválido visual por campo
- mensaje visible cercano al campo
- bloqueo del guardado
- permanencia del modal
- ausencia de cambios en la tabla

## Decisiones tomadas

### 1. Usar regex tolerantes a acentos en títulos visibles

La apertura del modal quedó validada con patrones como:

- `/l[ií]nea/i`

Eso evita fallos por diferencias entre catálogo, DOM y texto renderizado.

### 2. Validar obligatoriedad por todos los campos realmente vaciables

El caso ya no se quedó solo en `Nombre`.

Ahora el test:

- intenta validar obligatoriedad en cada campo objetivo del modal
- confirma si el campo está habilitado
- intenta vaciarlo solo si la UI real lo permite
- omite con trazabilidad los campos deshabilitados o no vaciables

### 3. Mantener la validación de formato en el campo textual editable

El catálogo describe explícitamente errores de formato sobre el campo de nombre, por eso la validación de:

- caracteres no permitidos
- texto inválido general

se mantuvo sobre el campo textual editable del modal.

### 4. Reutilizar helpers ya estabilizados de edición

Se reutilizaron patrones de:

- navegación a `Comunes`
- apertura flexible del modal
- localización robusta de campos
- captura de errores visibles por campo

## Diferencias UI vs catálogo

### 1. El catálogo asume campos vaciables sin restricciones

La UI real no siempre permite vaciar todos los campos visibles del modal. Algunos aparecen deshabilitados o derivados.

### 2. La cobertura correcta depende del comportamiento real de la UI

Para mantener fidelidad al caso sin inventar interacciones imposibles:

- se validan los campos realmente vaciables
- se documentan los omitidos
- no se fuerza cobertura artificial sobre controles bloqueados

## Patrones reutilizables

### 1. No asumir que los títulos visibles vendrán sin acentos

Cuando el flujo dependa de un texto visible de UI:

- preferir regex como `l[ií]nea`, `edici[oó]n`, `configuraci[oó]n`
- o normalizar texto antes de comparar cuando el helper lo permita

### 2. En validaciones negativas, distinguir entre `editable` y `vaciable`

Si el caso pretende validar obligatoriedad:

- primero confirmar que el control está habilitado
- después confirmar que realmente puede quedar vacío
- si no puede vaciarse, no forzar la ruta
- dejar trazabilidad del motivo de omisión

### 3. Los errores deben verificarse cerca del campo

Cuando el modal esté disponible, conviene seguir validando:

- mensaje visible cercano al campo
- señal visual de error
- bloqueo del guardado
- modal aún abierto

### 4. La tabla no debe mutar en validaciones negativas

Después de cada intento inválido:

- el modal debe seguir visible
- la fila base no debe reflejar cambios

## Recomendaciones

- Mantener `E36-C-03.1` como caso negativo por campo, no como error genérico único.
- Validar obligatoriedad sobre todos los campos realmente vaciables del modal.
- No tratar como bug funcional un campo que la propia UI muestra deshabilitado o no vaciable.
- Seguir usando la UI real como fuente de verdad antes de extender cobertura a otros campos del formulario.
