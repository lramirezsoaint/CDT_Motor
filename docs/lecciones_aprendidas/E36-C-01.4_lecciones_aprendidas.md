# E36-C-01.4 - Lecciones Aprendidas

## Objetivo

Documentar los problemas encontrados al implementar el caso `E36-C-01.4` y las decisiones que permitieron estabilizar su automatización en Playwright.

Este documento sirve como base de conocimiento para futuros casos que reutilicen patrones similares dentro del módulo `Comunes > Subcanales`.

## Contexto del caso

- Caso: `E36-C-01.4`
- Módulo: `Comunes > Subcanales`
- Flujo esperado:
  - entrar a `Distribución`
  - abrir `Comunes > Subcanales`
  - tomar la primera fila disponible
  - abrir el modal de edición
  - editar `Código Subcanal`, `Nombre Subcanal`, `Código Canal` y `Estado`
  - validar autocompletado `Código Canal -> Nombre Canal`
  - presionar `Actualizar`
  - validar mensaje de éxito y persistencia en tabla

## Problemas y soluciones

### 1. Este caso es efectivamente una variante de E36-C-01.2

**Problema**

El riesgo principal era reimplementar toda la lógica de edición de `Grupo Producto` con copy/paste para `Subcanales`.

Eso habría creado deuda técnica y más puntos frágiles para mantener.

**Solución**

Se extrajo un helper compartido:

- `tests/e2e/bloque-1/_shared/comunes-edit.ts`

Ese helper concentra lo que ya se había aprendido en `E36-C-01.2`:

- apertura flexible de modales
- búsqueda híbrida de campos
- soporte a `data-testid`/`id` compactos
- edición solo de campos habilitados
- tratamiento correcto de combos reales

### 2. Los modales de edición en Comunes deben resolverse por contexto y no por texto exacto

**Problema**

La familia E36 ya mostró que los títulos visuales de modal pueden variar o no ser lo suficientemente confiables para automatizar por texto exacto.

**Solución**

Se mantuvo el patrón:

- usar el `dialog` visible más reciente
- validar que el modal contenga el keyword funcional de la entidad (`subcanal|canal`)
- evitar dependencia rígida de un heading único

### 3. `Código Canal` debe tratarse como combobox real

**Problema**

Igual que en `Grupo Producto`, el campo relacionado con la entidad padre no debe asumirse como input simple.

En este tipo de formulario, el control visual puede ser:

- `role="combobox"`
- `readonly`
- con `id` o `data-testid` compactos

**Solución**

Se reutilizó el patrón del helper:

- primero buscar por label visible
- luego por `role="combobox"`
- después por `id`, `name` y `data-testid` compactados

Esto permitió tratar `Código Canal` como selector real de opciones.

### 4. `Nombre Canal` debe modelarse como campo derivado

**Problema**

La regla central del caso no es solo editar un formulario, sino preservar la relación:

- `Código Canal` seleccionado
- `Nombre Canal` autocompletado y no editable

**Solución**

El test valida explícitamente:

- `Nombre Canal` está deshabilitado
- al cambiar `Código Canal`, `Nombre Canal` cambia automáticamente
- la tabla final refleja la combinación consistente

Este patrón debe mantenerse para cualquier caso donde exista una relación padre-hijo visible en el modal.

### 5. Editar solo campos habilitados hace el flujo más robusto

**Problema**

Aunque el documento define qué campos son editables, la UI real puede condicionar ciertos controles según el estado del registro o la implementación actual.

**Solución**

Se mantuvo la regla aprendida:

- editar solo los campos habilitados
- omitir silenciosamente los deshabilitados
- fallar solo si ningún campo relevante es editable

Esto reduce falsos negativos por diferencias menores del frontend.

### 6. La tabla sigue siendo la validación de negocio más fuerte

**Problema**

Un modal puede cerrarse y un toast puede mostrarse, pero eso no garantiza persistencia real.

**Solución**

Después del guardado se valida en tabla:

- nuevo código subcanal
- nuevo nombre
- nuevo código canal
- nuevo estado
- nueva fecha/hora, si la columna `Modificado` está visible

Esta sigue siendo la mejor confirmación observable del negocio.

## Diferencias UI vs documento

### 1. El documento habla de "Editar Subcanal", pero la automatización no depende de ese texto exacto

La implementación se apoyó en contexto visual del modal, no en una sola cadena.

### 2. El comportamiento clave no es la edición del nombre del canal

El documento deja claro que `Nombre Canal`:

- no es editable
- depende del código seleccionado

La automatización lo trató como campo derivado, no como input manual.

## Patrones reutilizables

### 1. Helper único para edición en Comunes

Para futuros casos E36 similares:

- reutilizar `comunes-edit.ts`
- no volver a copiar lógica de modal/campo/combobox

### 2. Para relaciones derivadas

Cuando exista patrón:

- `Código X`
- `Nombre X`

la automatización debe:

- cambiar el código
- esperar cambio automático del nombre
- validar que el nombre no sea editable

### 3. Para combos reales

Antes de usar `fill()` sobre cualquier control:

- verificar si el DOM lo expone como `combobox`
- revisar `data-testid`
- revisar `id` compactado

## Recomendaciones

- Reutilizar el helper compartido en próximos casos de edición de `Comunes`.
- Si aparece otro formulario con relación derivada, no modelarlo como input libre.
- Seguir leyendo `docs/lecciones_aprendidas/` antes de implementar nuevos E36 para evitar volver a introducir lógica duplicada.
