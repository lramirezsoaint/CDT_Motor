# E36-C-01.2 - Lecciones Aprendidas

## Objetivo

Documentar los problemas encontrados al implementar el caso `E36-C-01.2` y las decisiones que permitieron estabilizar su automatización en Playwright.

Este documento sirve como base de conocimiento para futuros casos que reutilicen patrones similares dentro del módulo `Comunes > Grupo Producto`.

## Contexto del caso

- Caso: `E36-C-01.2`
- Módulo: `Comunes > Grupo Producto`
- Flujo esperado:
  - entrar a `Distribución`
  - abrir `Comunes > Grupo Producto`
  - tomar la primera fila disponible
  - abrir el modal de edición
  - editar campos habilitados
  - validar relación `Código Línea -> Nombre Línea`
  - presionar `Actualizar`
  - validar mensaje de éxito y persistencia en tabla

## Problemas y soluciones

### 1. El modal real no debe resolverse con un único título rígido

**Problema**

Al inicio se asumió que el modal siempre mostraría exactamente `Editar Producto`.

En la práctica, la UI mostró variantes del flujo donde el contenido visible seguía siendo de `Producto`, pero el texto del encabezado no siempre coincidía exactamente con esa cadena.

**Señales observadas**

- el click del lápiz ocurría
- la prueba fallaba diciendo que el modal no abría
- visualmente sí había un modal relacionado a `Grupo Producto`

**Solución**

Resolver el modal por contexto funcional, no por un solo texto exacto:

- usar el `dialog` visible más reciente
- validar que el modal contenga texto relacionado a `producto`
- no amarrar el flujo a una única cadena exacta del heading

### 2. `Código Línea` no es un textbox, es un combobox real

**Problema**

El caso falló varias veces porque `Código Línea` se estaba buscando como si fuera un input tradicional o un campo accesible solo por label.

La UI real renderiza este control como:

- `role="combobox"`
- `readonly`
- `data-testid="codigoLinea"`
- `id="codigoLinea"`

**Señales observadas**

- el campo era visible en pantalla
- el test seguía diciendo que no encontraba `codigo linea`
- el HTML real mostraba claramente `data-testid="codigoLinea"`

**Solución**

Buscar este control como combobox real y además soportar sus identificadores concretos:

- `role="combobox"`
- `id="codigoLinea"`
- `data-testid="codigoLinea"`

Regla para próximos casos:

- si un control visualmente es desplegable, no asumir `input.fill()`
- primero revisar si se trata de un `combobox`, `button`, `readonly input` o componente híbrido

### 3. Los labels visuales no siempre coinciden con el nombre técnico del atributo

**Problema**

El label visible era `Código Línea`, pero el DOM usaba naming compacto:

- `codigoLinea`
- `nombreLinea`
- probablemente `metodoValoracion`

Buscar solo por texto con espacios (`codigo linea`) no fue suficiente.

**Solución**

Agregar una estrategia dual:

- búsqueda por label visible
- búsqueda por clave compacta sin espacios ni tildes para `id`, `name` y `data-testid`

Esto permitió alinear mejor el nombre funcional del negocio con el naming técnico del frontend.

### 4. En formularios de edición no se debe forzar que todos los campos sean editables

**Problema**

La descripción del caso enumeraba campos esperados, pero en la UI real algunos pueden aparecer deshabilitados según el estado del registro, la configuración o la implementación actual.

Forzar edición sobre todos los campos vuelve frágil la automatización.

**Solución**

La prueba debe:

- editar solo los campos que estén habilitados
- omitir silenciosamente los que estén deshabilitados
- fallar solo si no existe ningún campo editable o si se rompe una regla de negocio clave

Excepción:

- `Nombre Línea` sí debe seguir validándose explícitamente como no editable

### 5. `Nombre Línea` debe validarse como campo derivado, no como entrada manual

**Problema**

Al tratar todos los campos de forma uniforme, se pierde la regla de negocio más importante del caso: `Nombre Línea` depende de `Código Línea`.

**Solución**

Modelar `Nombre Línea` como campo derivado:

- comprobar que esté deshabilitado
- cambiar `Código Línea` solo si el combobox está habilitado
- esperar que `Nombre Línea` cambie automáticamente
- validar consistencia entre ambos valores después del guardado

### 6. Las capturas del usuario son evidencia de implementación, no solo contexto

**Problema**

Durante la implementación hubo ambigüedad entre el caso escrito y lo que realmente renderiza la UI.

**Solución**

Cuando el usuario comparte capturas o HTML del componente:

- tratarlas como fuente primaria de verdad para selectores reales
- incorporar `id`, `data-testid`, `role` y estado visible del control
- ajustar el test a la UI observada antes de insistir con supuestos del catálogo

En este caso, la captura del usuario resolvió la parte crítica del selector de `Código Línea`.

## Reglas reutilizables para próximos casos de Comunes

### 1. Verificar primero si el control es `input` o `combobox`

Antes de automatizar un campo:

- revisar si permite `fill()`
- verificar si usa `role="combobox"`
- buscar `data-testid` e `id` compactos

### 2. Usar selectores híbridos

La estrategia más estable en este módulo fue:

- label visible
- `role`
- `data-testid`
- `id` compactado

No depender de solo una de esas dimensiones.

### 3. Mantener la prueba enfocada en reglas de negocio

En este flujo lo importante no es que todos los inputs existan, sino que:

- el modal abra
- los campos editables cambien
- `Nombre Línea` no sea editable
- `Código Línea` gobierne a `Nombre Línea`
- el sistema confirme guardado
- la tabla refleje el cambio

## Resultado útil para futuras implementaciones

Para casos nuevos de `Comunes > Grupo Producto` o módulos parecidos:

- asumir que los combos pueden ser `readonly inputs` con `role="combobox"`
- revisar siempre `data-testid`
- compactar nombres de labels para mapear `codigo linea -> codigoLinea`
- no forzar edición de campos deshabilitados
- modelar los campos derivados como reglas de negocio explícitas
