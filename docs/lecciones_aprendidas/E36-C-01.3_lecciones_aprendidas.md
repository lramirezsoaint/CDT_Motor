# E36-C-01.3 - Lecciones Aprendidas

## Objetivo

Documentar los problemas encontrados al implementar el caso `E36-C-01.3` y las decisiones que permitieron estabilizar su automatización en Playwright.

Este documento sirve como base de conocimiento para futuros casos que reutilicen patrones similares dentro del módulo `Comunes > Canales`.

## Contexto del caso

- Caso: `E36-C-01.3`
- Módulo: `Comunes > Canales`
- Flujo esperado:
  - entrar a `Distribución`
  - abrir `Comunes > Canales`
  - tomar la primera fila disponible
  - abrir el modal de edición
  - editar `Código`, `Nombre` y `Estado`
  - presionar `Actualizar`
  - validar mensaje de éxito y persistencia en tabla
  - validar comportamiento estable si existen datos asociados

## Problemas y soluciones

### 1. No depender de un título rígido del modal

**Problema**

El caso pedía validar `Editar Canal`, pero en la práctica los títulos de modales en este proyecto no siempre son suficientemente estables para automatizar contra una cadena exacta.

**Solución**

Resolver el modal por contexto funcional:

- capturar el `dialog` visible más reciente
- validar que el contenido del modal pertenezca al flujo de `Canales`
- no depender exclusivamente del texto exacto del heading

Esto sigue la misma regla aprendida en `E36-C-01.2`.

### 2. En edición simple, los campos deben tratarse como "editar si están habilitados"

**Problema**

Aunque el documento describe `Código`, `Nombre` y `Estado` como editables, en este codebase los formularios pueden variar según el estado del registro o la implementación actual.

Forzar edición sobre todos los controles vuelve la prueba más frágil.

**Solución**

Aplicar el patrón:

- ubicar los campos esperados
- editar solo los que estén habilitados
- fallar solo si el modal abre pero no existe ningún campo editable

Esto evita que el test sea quebradizo frente a pequeñas variaciones del frontend.

### 3. El mensaje de éxito sí aparece, pero no siempre es estable capturarlo como "toast visible"

**Problema**

El caso falló inicialmente porque la automatización no lograba detectar el mensaje esperado, aunque el `error-context` mostraba claramente:

- `¡Cambios guardados correctamente!`

El mensaje vive dentro de la región de notificaciones, y su aparición/vida útil puede ser más rápida que una validación basada únicamente en `isVisible()` del locator del toast.

Además, el texto observado en snapshot apareció con codificación visual:

- `Â¡Cambios guardados correctamente!`

**Solución**

Validar el resultado usando `expect.poll()` sobre el texto visible del `body`, buscando:

- `cambios guardados correctamente`
- o el mensaje de datos asociados

Luego usar regex tolerante para la confirmación de éxito:

- `/cambios guardados correctamente/i`

Esto evita depender de la codificación visual del signo inicial o de la vida útil exacta del toast.

### 4. Los snapshots del error pueden mostrar la verdad aunque la aserción original falle

**Problema**

Hubo una situación donde el test fallaba diciendo que no había mensaje visible, pero el snapshot del run sí mostraba el toast en pantalla.

**Solución**

Cuando un test falle por ausencia de mensaje:

- revisar primero `error-context.md`
- comparar con la captura
- ajustar la estrategia de espera al comportamiento real de la UI

Regla práctica:

- si el snapshot sí contiene el mensaje, el problema suele ser de sincronización o de selector, no necesariamente del producto

### 5. La validación de "datos asociados" debe ser complementaria, no destructiva

**Problema**

El caso incluye una trampa importante: algunos registros pueden tener subcanales asociados.

Si eso ocurre:

- el sistema debe informar `El registro que desea modificar cuenta con datos asociados. Favor de validar.`
- pero no debe romperse

**Solución**

Modelar este comportamiento como alternativa válida al mensaje de éxito:

- éxito: `cambios guardados correctamente`
- o mensaje de advertencia por datos asociados

Y en ambos casos exigir que:

- el flujo no explote
- el modal no quede en estado inconsistente

### 6. En Canales, la tabla fue una fuente confiable para validar persistencia

**Problema**

La confirmación visual sola no basta; el caso exige que la tabla refleje cambios y, si está visible, la fecha/hora se actualice.

**Solución**

Después de confirmar el resultado visible:

- buscar la fila por los nuevos valores esperados
- validar `Código`, `Nombre` y `Estado`
- validar `Modificado` si la columna existe

Esto mantiene el enfoque de negocio del caso y evita falsos verdes.

## Diferencias UI vs documento

### 1. El documento habla de "Editar Canal", pero la automatización no debe depender de ese texto exacto

En la UI real, el mejor ancla fue el modal visible del flujo `Canales`, no un heading único e inmutable.

### 2. El mensaje de éxito puede verse con codificación distinta

La UI mostró el texto correcto a nivel funcional, pero el snapshot evidenció variación en el render:

- `¡Cambios guardados correctamente!`
- `Â¡Cambios guardados correctamente!`

Por eso conviene validar por regex estable y no por coincidencia exacta con símbolos especiales.

## Patrones reutilizables

### 1. Para edición en módulos Comunes

- abrir el modal por contexto, no por título rígido
- editar solo campos habilitados
- validar negocio en tabla, no solo en modal

### 2. Para mensajes transitorios

- usar `expect.poll()` sobre texto visible del `body`
- preferir regex estables sin depender de signos especiales o de la estructura exacta del toast

### 3. Para escenarios con dependencias

- tratar advertencias de datos asociados como camino funcional esperado
- comprobar que el sistema no se rompa aunque el registro tenga relaciones

## Recomendaciones

- Reutilizar este patrón para futuros casos de edición simples en `Comunes`.
- Si un mensaje visual existe en snapshot pero no en el test, priorizar ajuste de sincronización antes de asumir bug del producto.
- Seguir leyendo `docs/lecciones_aprendidas/` antes de nuevos casos E36 para evitar reintroducir rigidez en modales y toasts.
