# E36-C-03.5 - Lecciones Aprendidas

## Objetivo

Documentar los hallazgos al implementar `E36-C-03.5`, enfocado en validaciones negativas por campo dentro de `Comunes > Configuración de Parches`.

## Hallazgos

- El caso quedó implementado, pero la corrida actual no pudo ejecutarse funcionalmente porque la vista no tenía registros editables.
- La ausencia de datos en este caso no debe reportarse como bug del formulario, sino como bloqueo de ambiente o precondición no cumplida.
- `Configuración de Parches` tiene varios campos complejos y no homogéneos:
  - combos
  - campos derivados
  - campos numéricos
  - campos opcionales y obligatorios mezclados

## Decisiones tomadas

- Se implementó el caso igualmente para dejarlo listo cuando existan registros.
- El test falla temprano con mensaje explícito:
  - `[DATA] No hay registros disponibles en Configuración de Parches para validar edición inválida por campo.`
- Se dejó preparada la validación de:
  - obligatoriedad en `UoA Antes`, `UoA Después` y `Porcentaje`
  - formato inválido en `Porcentaje`

## Patrones reutilizables

- Cuando un caso depende de una fila editable y no hay datos, el test debe fallar con clasificación `DATA`, no degradarse a una validación superficial.
- En formularios complejos, conviene dejar implementado el flujo negativo completo aunque la data aún no exista.
- Los campos obligatorios numéricos deben tener una validación específica de formato además de la obligatoriedad.

## Recomendaciones

- Reejecutar `E36-C-03.5` cuando la vista de `Configuración de Parches` tenga al menos una fila editable.
- Mantener la clasificación `DATA` mientras la tabla siga vacía.
- No reemplazar este bloqueo por asserts débiles solo para volver verde el caso.
